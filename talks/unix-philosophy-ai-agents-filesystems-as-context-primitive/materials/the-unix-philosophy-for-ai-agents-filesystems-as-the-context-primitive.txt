Agents work one layer above the ﬁlesystem
TOO LOW — FUSE AND POSIX
Byte-level access
open, seek, read(offset, length). Every call is a round 
trip.
Efficient locally, costly 
remotely
Fine against a local disk. Expensive across a network, 
and the agent gains nothing from the extra precision.
THE LAYER WE WANT
The harnesses already work 
here
Their tools are not filesystem calls, and none of them 
operate on byte offsets.
Operations execute at the 
source
Today a source is mounted through to the client and 
treated as an ordinary filesystem, which makes 
transfer, search and write-back inefficient.
TOO HIGH — OPERATIONS MODELLED PER SOURCE
Large surface area
Standardising operations at the level each source 
already thinks in means every implementer builds a lot 
and keeps little flexibility.
Where this sits today
MCP resources carry read and list. Anything richer 
arrives as per-server tools, so the rich operations are 
never shared.
Is this FUSE?
FUSE specifies byte-level access to a local mount.
Which layer should the protocol specify? That is what the working group exists to answer.
Bloomberg
Is this HTTP again?
Where HTTP already carries the semantics, adopt them rather 
than specifying parallel ones.
Is this File Uploads?
File Uploads declares user-selected file inputs. Its charter puts 
server-side content with Resources.

Unix is broad. We borrow one pattern, because models are already trained on these operations and the harnesses converged on them 
independently.
What we borrow from Unix
$CLASSIC UNIX PATTERN /OUR AGENT ADAPTATION
grep sort uniq| |
small tools connected through a simple convention
Do one thing well
grep searches. sort orders. Neither tool knows the other.
Discovery precedes reading
ls names what is there. grep looks inside it.
Outputs become inputs
grep ERROR app.log | sort | uniq -c
ADAPT
retrieve analyse synthesise
/thread/
source.md
/task/
findings.j
son
steps compose through stable, named handoffs
Small operations
list(path), read(path), write(path, data), search(path, query), discover(path).
Discovery and search run at the source
Matching happens where the content already is, so only the results travel.
Operations compose over a path
discover /thread, then search /thread, then read the matches. One 
vocabulary against any mount.
Borrow the goal: composability. Adapt the mechanism: paths and file operations.
Text streams form a common interface
A program reads a byte stream, without the producer's internals.
Stable, path-addressed handoffs
retrieve writes /thread/source.md. analyse reads that path. Either step 
can be replaced, and models, tools and people read the same file.
