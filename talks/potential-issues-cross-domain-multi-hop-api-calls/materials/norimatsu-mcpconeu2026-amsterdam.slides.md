## Slide 12 — OAuth Identity and Authorization Chaining Across Domains
**Text.** AGNTCon + MCPCon Europe 2026 / OAuth Identity and Authorization Chaining Across Domains* / Trust Domain A / Trust Domain B / User / MCP Client / MCP Server / AS-A / API Server / AS-B / Token Exchange (Internal to External) / JWT Authorization Grant / No Need to get an appropriate token from AS in Domain B / No Information leaks from Domain A to B / No Potential for fraudulent use of a token issued by AS in Domain A / *: Internet Draft: OAuth Identity and Authorization Chaining Across Domains (https://www.ietf.org/archive/id/draft-ietf-oauth-identity-chaining-17.html) / € : Access Token for MCP Server in Domain A / 🎫 : JWT-formatted Assertion from Domain A to B without sensitive info / $ : Access Token for API Server in Domain B
**Shows.** Same architecture diagram, now showing the full proposed flow: MCP Server exchanges its Domain-A token internally with AS-A for a JWT-formatted assertion (ticket icon) that carries no sensitive info, sends that assertion across the boundary to AS-B via a "JWT Authorization Grant," and AS-B returns a proper Domain-B access token. Three green callouts state the resulting benefits: no need to pre-fetch a Domain-B token, no information leak, and no potential for fraudulent token use.

## Slide 50 — Secure External Authorization: Pushed Authorization Request
**Text.** AGNTCon + MCPCon Europe 2026 / Secure External Authorization: Pushed Authorization Request*1 / The contents of an authorization request are pushed to AS. / The authorization request only include "client_id" and "request_uri", which is a key to fetch the contents registered inside AS. / [Effect] / • An attacker cannot modify parameters like "redirect_uri" the request. / • The attacker cannot impersonate a client to register its authorization request contents. / redirect / Parameters are conveyed by query parameters / GET: Authorization Request (client_id, redirect_uri, scope, etc..) / Parameters are conveyed by HTTP POST / POST: Request (client_id, redirect_uri, scope, etc..) / client authentication register parameters / Response (request_uri) / redirect / GET: Authorization Request (client_id, request_uri) / fetch parameters / *1: RFC 9126 OAuth 2.0 Pushed Authorization Requests (https://www.rfc-editor.org/rfc/rfc9126.html)
**Shows.** Two stacked sequence diagrams contrasting classic authorization requests (parameters conveyed via GET query string, which an attacker could tamper with) against Pushed Authorization Requests (client POSTs the full parameter set to AS with client authentication first, AS returns a request_uri, and only client_id plus that opaque request_uri travel via the browser redirect) — this is the fix recommended for the "not verify redirect_uri" vulnerability exploited in the Type 3 phishing attack.
