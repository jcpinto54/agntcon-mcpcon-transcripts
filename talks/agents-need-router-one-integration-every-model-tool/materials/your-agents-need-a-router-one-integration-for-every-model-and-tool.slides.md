## Slide 4 — Where a router fits in the agent stack
**Text.** ARCHITECTURE / Where a router fits in the agent stack / The agent calls one contract. The platform declares traffic intent once. Control plane (Providers · credentials · routes · quotas · tools · policy) / Envoy data plane (Requests · retries · limits · telemetry · egress) / UPSTREAM ESTATE — Models & tools: Hosted providers, Self-hosted inference, MCP servers — metrics traces logs

## Slide 5 — The application stays boring — on purpose
**Text.** DEVELOPER EXPERIENCE / The application stays boring — on purpose / The agent speaks a single OpenAI-compatible API. / 01 Change the base URL once — The SDK integration remains familiar; traffic decisions leave application code. / 02 Request a logical model — Routes can override provider-specific model identifiers downstream. / 03 Keep secrets behind the router — Provider credentials belong to platform configuration, not agent workloads. / from openai import OpenAI / client = OpenAI( base_url="https://router.example/v1", api_key=router_token, ) / reply = client.chat.completions.create( model="claude-4-sonnet", messages=messages, ) / # No provider SDK. No provider key. / # "claude-4-sonnet" is a logical name.
**Shows.** A Python code sample showing an application using the standard OpenAI SDK, pointed at the router's base URL with a router token instead of a provider key, and requesting a model by a logical name ("claude-4-sonnet") rather than a provider-specific identifier — demonstrating that the application code never changes regardless of which upstream provider actually serves the request.

## Slide 6 — One logical model, many possible paths
**Text.** MODEL VIRTUALIZATION / One logical model, many possible paths / Virtualization separates what the agent asks for from what each upstream provider calls the model. / CLIENT REQUEST — claude-4-sonnet — A stable, readable application-level name. The route maps it to the provider-specific identifier. / Pattern A · split traffic — Use weights to compare providers or distribute compatible capacity. Bedrock: anthropic.claude-sonnet-4-20250514-v1:0 ↔ GCP: claude-sonnet-4@20250514 — weight: 50 / 50 / Pattern B · protect availability — Use priorities plus retry policy to move to a healthy fallback. primary priority: 0 → fallback priority: 1 — retry + health signals / weights distribute traffic | priorities express failover order.
**Shows.** A client request for the logical model "claude-4-sonnet" branches into two route-design patterns: Pattern A shows the same logical name mapped to two different provider-specific identifiers (Bedrock's and GCP's naming conventions) split 50/50 by weight; Pattern B shows a primary backend (priority 0) with a fallback backend (priority 1) triggered by retry and health signals — illustrating two different ways the router can resolve one logical model name to multiple real upstream paths.

## Slide 7 — Declare the route, not the SDK logic
**Text.** BACKEND POOL EXAMPLE CONFIGURATION / Declare the route, not the SDK logic / The logical model name is used for routing; Envoy retries across prioritized backends when the policy says it may. / apiVersion: aigateway.envoyproxy.io/v1beta1 kind: AIGatewayRoute metadata: name: claude-resilient spec: rules: - matches: - headers: - name: x-ai-eg-model value: claude-4-sonnet type: Exact backendRefs: - name: bedrock modelNameOverride: anthropic.claude-sonnet-4-... priority: 0 - name: gcp-anthropic modelNameOverride: claude-sonnet-4@20250514 priority: 1 / # BackendTrafficPolicy → generated HTTPRoute retry: { numAttemptsPerPriority: 1, numRetries: 5 } retryOn: connect-failure, retriable-status-codes, 500 / 1 · Virtualize the name — modelNameOverride translates the logical request to each provider's exact upstream identifier. claude-4-sonnet ↔ provider IDs / 2 · Express the order — The first backend is priority 0; the next healthy backend is priority 1. primary → fallback / 3 · Make failover actionable — Priority alone is not a retry policy. Attach BackendTrafficPolicy to define eligible retry triggers and timing. connect failure · 5xx · retry
**Shows.** A full YAML AIGatewayRoute manifest matching requests on an exact model header (x-ai-eg-model: claude-4-sonnet) and routing them to two prioritized backendRefs (bedrock priority 0, gcp-anthropic priority 1), each with its own modelNameOverride, plus a BackendTrafficPolicy snippet defining retry attempts and which failure conditions (connect-failure, retriable status codes, 500) trigger a fallback — the concrete Kubernetes-style config implementing the two patterns from the previous slide.

## Slide 8 — Fine-grained budget control with Quotas and Rate Limits
**Text.** SPEND CONTROL / Fine-grained budget control with Quotas and Rate Limits / Configure how much capacity the platform has on each backend and model. Set how much each team, user or tenant can spend. / Quota Policies — Allow platform owners to set quotas per upstream backends and models, with graceful fallback policies between them when exhausted. / Rate limiting — Fine-grained controls over user token consumption for each available model. Configure budgets for users and tenants. / EXAMPLE · token budget accounting / Default model bucket · 10,000 tokens / 1h — 7,200 used / Tenant "acme" bucket · 5,000 tokens / 1h — 4,450 used / next matching requests can be rejected at the policy boundary / model name + dimension (x-tenant-id) + token cost → quota / ratelimit bucket / Useful controls: per-model limits · header-selected tenant buckets · CEL token-cost expression · shadow mode before enforcement.
**Shows.** Two horizontal usage-bar gauges showing live token-budget accounting: a "Default model bucket" at 7,200 of 10,000 tokens used per hour (teal, about 72% full), and a "Tenant 'acme' bucket" at 4,450 of 5,000 tokens per hour (orange, about 89% full, nearly exhausted); below, a small pipeline diagram shows how model name + a tenant dimension header + a token-cost expression combine into a specific quota/rate-limit bucket.

## Slide 9 — Cap the surprise before it happens
**Text.** UPSTREAM BACKEND QUOTAS / Cap the surprise before it happens / Attach a token budget to the AI service backend; carve out tenant-level capacity with a request-header selector. / apiVersion: aigateway.envoyproxy.io/v1alpha1 kind: QuotaPolicy metadata: name: team-token-budget spec: targetRefs: - group: aigateway.envoyproxy.io kind: AIServiceBackend name: openai perModelQuotas: - modelName: gpt-4 quota: costExpression: "input_tokens + output_tokens * 6u" defaultBucket: limit: 10000 duration: "1h" - modelName: gpt-5 quota: costExpression: "input_tokens + output_tokens * 6u" defaultBucket: limit: 1000 duration: "1h" / 1 · Match the route exactly — modelName matches the route backend's modelNameOverride. gpt-4 ↔ modelNameOverride / 2 · Price what matters — CEL can weight token classes. Here, output tokens burn six units each. output_tokens * 6u / 3 · Roll out safely — Configure shadow mode to evaluate and emit telemetry without blocking traffic. observe → tune → enforce
**Shows.** A full YAML QuotaPolicy manifest attaching per-model token quotas (gpt-4: 10,000 tokens/hour; gpt-5: 1,000 tokens/hour) to an AIServiceBackend named "openai," using a CEL cost expression that weights output tokens six times more than input tokens — the concrete configuration implementing the quota concept introduced in the previous slide, plus guidance to roll it out first in shadow (observe-only) mode.

**Shows.** A diagram where a "Research agent" connects to a single MCP endpoint exposed by an "Agent Router MCPRoute" box (configured with toolSelector, authorization, upstream auth, and operations sub-settings), which aggregates and filters access to three real backend MCP servers (github, context7, jira), each shown with its filtered tool scope and an example allowed tool name — illustrating per-agent tool visibility enforced centrally at the gateway rather than in each MCP server.
